Serverless Inteligente, en detalle

Arquitectura sin servidores

Una API de comercio electrónico que escala a cero

Navegador → API Gateway → Lambda → DynamoDB, con observabilidad de extremo a extremo

Ver caso técnico completo

La actividad

Construcción y despliegue de una aplicación de comercio electrónico sobre una arquitectura completamente sin servidores. Tres recursos —usuarios, pedidos y productos— expuestos por una puerta de enlace de API, resueltos por funciones independientes y persistidos en una base de datos NoSQL. Un sitio estático alojado en almacenamiento de objetos consume esa API desde el navegador, y toda la actividad queda registrada con métricas y una alarma que notifica por correo al superar su umbral.

El desafío

El obstáculo no fue construir los servicios sino hacer que los controles de seguridad convivieran con el navegador. Tres problemas distintos —el método de verificación previa exigiendo credenciales, las respuestas de error sin encabezados de origen cruzado, y el alcance de la política de autorización— producían exactamente el mismo mensaje genérico de fallo de red. Diagnosticar eso obliga a razonar por eliminación, no por el error.

La solución

Control de acceso en dos capas independientes: un autorizador que valida la credencial y emite una política, y una clave asociada a un plan de uso que limita el consumo. La primera responde quién eres; la segunda, cuánto puedes pedir. Comprometer una no anula la otra.

En la capa de datos, un índice secundario permite consultar los pedidos de un cliente sin recorrer la tabla completa. La diferencia es económica además de técnica: se factura por lo que se lee, no por lo que se devuelve.

Herramienta técnica utilizada

La arquitectura se apoya en servicios gestionados de AWS. Las funciones están escritas en Python; el cliente del sitio es HTML, CSS y JavaScript sin dependencias externas.

API Gateway · entrada y control de acceso AWS Lambda · Python DynamoDB · índice secundario global Amazon S3 · sitio estático CloudWatch · registros y métricas SNS · notificación de alarma

Qué aprendí

El arranque en frío depende de lo que la función carga, no de lo que hace. Una función que solo importa la biblioteca estándar inicializa en 85 milisegundos; la misma función importando el kit de desarrollo tarda medio segundo. Por eso los clientes se declaran fuera del controlador: se crean una vez y se reutilizan.

El mismo síntoma puede tener causas opuestas. Una función invocada directamente falla si añade encabezados de origen cruzado, porque la plataforma ya los pone. La misma función tras una puerta de enlace falla si no los añade, porque ahí la plataforma no lo hace.

En serverless el perímetro es la identidad, no la red. La arquitectura no tiene red virtual ni subredes, y no le hacen falta: ningún servicio empleado vive dentro de una red del cliente.

Por qué elegí este proyecto

Podría haber elegido un proyecto que saliera bien a la primera. Elegí este precisamente porque no salió bien a la primera, y eso es lo que lo hace demostrable.

Es el único que puede evaluarse con datos medidos en lugar de descripciones: cada afirmación de este caso tiene detrás un número obtenido de los registros del propio sistema. El problema central fue de diagnóstico, no de construcción, y esa es la habilidad que se usa a diario en un equipo.

Además cubre el ciclo completo —diseño, seguridad, datos, interfaz, observabilidad y costo—, así que permite conversar sobre cualquiera de esas capas en vez de defender una sola dimensión.

Durante la revisión final encontré una vulnerabilidad de inyección en la capa de presentación: el nombre de un producto se insertaba como HTML en lugar de como texto. Lo relevante no es la técnica, que es conocida, sino dónde apareció: en un proyecto cuyo eje era la seguridad. La atención puesta en el perímetro había dejado desatendida la interfaz. Mantenerlo visible aquí es deliberado.
